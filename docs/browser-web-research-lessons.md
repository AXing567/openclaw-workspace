# 浏览器自动化 / 网页攻坚经验沉淀

更新时间：2026-03-20

## 适用范围
适用于：
- 公开网页资料搜索
- 页面结构分析
- 接口/请求观察
- 半自动抓取原型验证
- 需要真实浏览器上下文的复杂页面调研

不适用于：
- 稳定、低成本、海量通用搜索
- 明显违反目标站规则的批量采集
- 把单次打通经验误当成长期稳定基础设施

## 方法论

### 1. 先判断问题类型
网页任务失败时，先判断属于哪类：
- 环境问题
  - 缺依赖
  - 浏览器起不来
  - 动态库不全
- 目标站问题
  - JS 依赖重
  - 登录态要求
  - 页面结构复杂
- 风控问题
  - IP 风险
  - 频率限制
  - 机器人识别

不要一上来就下结论说“方案不行”。

### 2. 选路原则
- 轻量抓取：优先 `web_fetch` / `web_search`
- JS 重、要交互、要登录：切 `browser`
- 需要真实页面观察、请求链分析、复杂交互：优先浏览器自动化

### 3. 受限环境下的浏览器打通原则
优先选可局部修复、可控、无 sudo 依赖的路径：
- 本地补依赖
- 手动下载浏览器
- 显式指定浏览器 executablePath
- 用运行库路径补齐动态依赖

比起长时间等待系统级权限，这类方案更可控。

## 风险判断原则

### 社媒 / 平台风控
像小红书这类站点，失败往往未必是执行器本身失效，而更可能是：
- 出口 IP 风险
- 登录态异常
- 平台临时风控
- 页面挑战升级

遇到这类场景，要先诊断风控，不要误判为整个自动化路线不可用。

## 对后续工作的启发
- 以后类似网页攻坚任务，优先做“问题归类”，再做技术实现。
- 把“环境问题 / 风控问题 / 页面本身问题”分开看，能显著减少误判。
- 长期上，这类经验更适合沉淀在专题文档，不应把细实现全塞进长期记忆。
