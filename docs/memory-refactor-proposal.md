# MEMORY.md 精简重构方案（草案）

更新时间：2026-03-20

## 目标
把 `MEMORY.md` 从“长期记忆 + 部分任务经验混合体”压缩成：
- 更短
- 更稳定
- 更能直接指导未来行为
- 更少事件噪音

## 一、建议保留的内容

### 1. 身份与关系
- 用户叫阿星，默认这样称呼。
- 用户自述人格倾向为 INTJ。
- 我的名字是“虾丞相”。

### 2. 用户偏好与边界
- 用户偏好：在内部可自主推进的事情上，默认直接做完，不要频繁停下来征求“是否同意”；除非涉及外部动作、敏感操作或高风险变更。
- 可见性要求：只要更新长期记忆或关键文档，必须让用户能在工作区文件里直接看到，不要只在口头上说“记住了”。

### 3. 长期方法论
- OpenClaw 工具使用原则：优先采用内置一流工具而不是旧式技能或 shell 绕路；网页交互默认走 `browser -> snapshot -> act`；长任务按 `exec + process` 的前后台模型理解；工具可用性按 `tools.profile -> tools.byProvider -> tools.allow/deny` 分层判断。
- OpenClaw 能力增强原则：轻量网页获取优先 `web_search/web_fetch`，重交互或 JS/反爬页面切 `browser`；Skills 是任务流程固化层，Plugin 是平台能力扩展层；Skills 要控制数量和 token 成本，并按 workspace/shared/bundled 分层管理；host 执行必须同时按工具策略、exec 审批和 allowlist 三层理解。
- 工作流要求：长任务不能黑盒推进，必须有可见沉淀、明确状态和阻塞反馈；不能只靠口头承诺回报。

## 二、建议“改写后保留”的内容

### A. 浏览器/网页攻坚经验
现状问题：
- 现在写得偏“某次打通过的方案复盘”，颗粒度太细。

建议改写为：
- 网页攻坚方法论：公开网页调研、结构分析、接口观察、半自动抓取验证等任务，优先组合使用命令行联网、浏览器自动化与本地沉淀；遇到风控、依赖缺失或浏览器运行异常时，先判断环境和目标站限制，不轻易误判整体方案失效。
- 受限环境下的浏览器打通原则：优先选无 sudo、可局部补依赖、可显式指定浏览器路径与运行库的方案，避免过度依赖系统级安装权限。

### B. 长任务监督经验
现状问题：
- 现在有多条表述重复，而且混入了一个已经被否决的具体方案历史。

建议改写为：
- 长任务监督原则：状态反馈应基于真实进度变化与阻塞识别，避免依赖手工维护且容易失真的中间状态文件，尤其避免定时复读式汇报。

## 三、建议下沉到 docs/ 或 daily memory 的内容

### 1. 应下沉到 docs/
- 关于浏览器自动化具体实现细节：
  - 手动下载浏览器
  - `executablePath`
  - `LD_LIBRARY_PATH`
  - “无 sudo 本地补依赖”这类具体实现
- 这些更适合进专题文档，比如：
  - `docs/browser-automation-lessons.md`
  - 或已有 OpenClaw / tooling 笔记里

### 2. 应只保留在 daily memory
- “用户判断：基于手动维护 current-task.json 的监督/回报机制不可靠……”
- 这条是一次具体方案被否决的事件记录，价值主要在当天上下文，不适合长期单独占一条。
- 其长期可复用部分，已经被上面的“长任务监督原则”吸收。

## 五、当前结论

- 现在的 `MEMORY.md` 不是不能用，而是“有点开始长歪了”。
- 真正需要做的不是大删特删，而是：
  - 合并重复原则
  - 把事件型表述改写成抽象原则
  - 把实现细节下沉到 docs/
- 这样做完之后，长期记忆会更像“脑子”，daily memory 更像“日记”，docs 更像“知识库”。
