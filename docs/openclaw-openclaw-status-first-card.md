# OpenClaw Status First Card

## 结论

当需要判断 OpenClaw 当前能力、工具可用性、节点/网关状态、运行环境是否正常时，默认先看 `openclaw status`，而不是先靠文档记忆、猜测配置，或直接从某个单一工具失败倒推出整体现状。

## 适用场景

- 想确认当前 runtime、模型、工具、网关或节点是否在线
- 想判断某个失败是环境故障、工具策略限制，还是任务本身有问题
- 想做 OpenClaw 能力学习沉淀，补一张“实际排查入口”卡而不是继续写抽象边界卡

## 为什么先看 status

`openclaw status` 是最低成本的真实快照：

- 能快速看到当前代理/网关/节点是否正常
- 能帮助区分“平台没起来”和“任务不会做”
- 能把很多抽象规则落回真实运行态，减少纸面理解偏差

比起继续围绕 heartbeat 节奏、跳过条件、选题边界写卡，`status` 更接近真实排障入口，也更容易积累成通用经验。

## 默认动作

1. 先运行 `openclaw status`
2. 看输出更像哪一类：
   - **整体正常**：再决定是查具体工具、具体配置，还是结束
   - **部分异常**：记录异常层级（gateway / node / tools / auth / transport）
   - **命令不可用或信息不足**：再退回文档或更细分命令
3. 若要沉淀文档，优先记录“status 能回答什么、不能回答什么、下一跳去哪”

## 不该怎么做

- 某个工具一时报错，就直接推断 OpenClaw 整体不可用
- 没看当前运行态，就先写一堆抽象边界说明
- 把 `openclaw status` 当成只是给用户看的命令，而不是自己的首轮检查入口

## 实操口令

> 遇到 OpenClaw 能力/环境判断题，先看 `openclaw status`；先拿真实快照，再谈抽象规则。
