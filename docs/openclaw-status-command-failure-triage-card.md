# OpenClaw Status Command Failure Triage Card

## 结论

当 heartbeat 想用 `openclaw status` 获取真实运行态快照，但命令本身直接失败、且没有留下有效输出时，下一步不该假装已经拿到了状态，也不该立刻转入大范围排查；默认应把这次结果沉淀为**命令入口失效**这一类经验，并在当前轮停止扩张。

## 为什么单独记这一条

在 heartbeat 场景里，`openclaw status` 常被当作低成本、总览式入口。但如果入口本身失败，最容易犯的错有两个：

1. **误报现状**：把上一次成功的 status 印象当成这一次的实时状态。
2. **过度扩张**：为了补齐这次失败，立刻转去跑更多 CLI、日志、目录遍历，结果把一次低打扰心跳变成排障工程。

这两种都违背 heartbeat 的单轮、低噪音边界。

## 默认动作

1. 先确认失败事实：命令退出非零，且无可用输出。
2. 把问题归类为“状态入口失败”，不要归类成“系统已异常”。
3. 如果用户当前并未要求排障，只做短卡沉淀或直接安静跳过。
4. 只有当任务目标本来就是诊断 OpenClaw 故障时，才值得继续深挖下一层命令。

## 推荐表述

- “这轮没有拿到有效 status 输出，说明状态入口本身失败，不能据此反推当前系统状态。”
- “入口失败先记作待诊断信号，不自动升级成服务故障结论。”

## 避免的动作

- 沿用旧的 status 结果冒充当前快照
- 因一次命令失败就在 heartbeat 中展开全面排障
- 把 CLI 失败直接写成 gateway 宕机或系统不可用

## 实操口令

> heartbeat 里若 `openclaw status` 无输出失败，先把它当作“入口失效信号”，沉淀边界后收手；别拿旧快照顶替，也别顺势开大工程。
