# OpenClaw Status 文档落点卡

更新时间：2026-03-27

## 问题

跑完 `openclaw status` 后，常见误区是：
- 要么围着 status 输出继续拆很多碎卡
- 要么完全忽略它自带的 `next steps` / FAQ / docs 落点

结果是自己重复发明排查路线，而不是顺着现成文档入口下钻。

## 结论

`openclaw status` 的价值不只是“告诉你现在怎样”，还在于给出后续文档落点。
默认 follow-up 应优先判断：
1. 当前异常是否已被 status 指到明确文档入口
2. 该入口能否直接缩短下一步排查路径
3. 是否真的需要再额外沉淀一张新卡

## 默认做法

1. 先读 status 输出中的高价值异常和 `next steps`
2. 若已有明确 FAQ / docs 指针，先顺着它读
3. 只有在以下情况才值得额外写新卡：
   - status 没把关键边界说清
   - 本地执行中反复出现同一判断误区
   - 需要把零散说明压缩成未来可复用的选路规则

## 反模式

- 跑完 status 后，不看它给的下一跳，只围绕原始输出自我发挥
- 文档已有明确排查入口，却另外写一套重复的“可能怎么查”
- 因为一次 status 学习，就新建多张字段级碎卡，制造文档簇过密

## 一句话版

> `openclaw status` 不只是状态面板，也是文档路由器；先沿它给的入口下钻，再决定要不要自己补卡。
