# OpenClaw Status Failure Follow-up Scope Card

## 结论

当 heartbeat 中把 `openclaw status` 作为默认状态入口，但命令本身失败时，后续动作应先控制在**最小判别范围**：确认这是命令入口问题、环境瞬时问题，还是系统级异常信号；不要自动把一次失败扩写成整套排障工程。

## 默认顺序

1. **先承认入口失败，不复用旧快照**
   - 失败就是失败，不能拿上一次的 status 输出冒充当前状态。
   - heartbeat 文档沉淀应围绕“失败后的处理边界”，不是围绕旧结论继续发挥。

2. **再判断这次失败是否值得继续追一层**
   - 如果当前任务只是空闲学习沉淀：最多补一张处理边界卡，或做一次轻量分类，不再连续深挖。
   - 如果用户当前就在做节点/网关/配置排障：才值得继续往下一层确认。

3. **follow-up 只选一个最有判别力的问题**
   - 例如：
     - 是命令不存在/版本不匹配？
     - 是 CLI 可执行但子检查失败？
     - 是权限/环境变量/当前 shell 上下文异常？
   - 一轮 heartbeat 只处理其中一个，不默认全查。

## 为什么

`openclaw status` 失败是一个新信号，但它本身还不等于“系统坏了”。如果在 heartbeat 里把它直接放大成全套排障，很容易违背“低打扰、单轮闭合、不要把心跳扩成工程”的原则。

## 边界

适合 heartbeat 继续做的：
- 记录失败是独立状态，不复用旧状态
- 压缩 follow-up 的选择口径
- 说明什么时候该停在文档沉淀层

不适合 heartbeat 默认展开的：
- 连续跑多条系统诊断命令
- 顺手开始修配置/改环境
- 沿着失败信号扩成完整故障树

## 实操口令

> `status` 失败后，先问：这次我最需要分辨的唯一问题是什么？如果答不出唯一问题，就先停在“记录失败边界”这一层。
