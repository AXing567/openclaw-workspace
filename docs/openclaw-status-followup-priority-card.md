# OpenClaw Status Follow-up Priority Card

## 结论

`openclaw status` 已经给出总览后，下一步不要机械地继续围绕输出逐项抄写；应优先判断**哪一类 follow-up 最值得追**，把 status 当成分诊入口，而不是待完整转录的清单。

## 默认优先级

看到 status 输出后，按这个顺序判断：

1. **会阻塞当前任务的异常**
   - gateway 未运行
   - node / plugin / provider 明显失联
   - 权限、路径、配置错误会立刻影响执行

2. **高风险安全问题**
   - critical / high 级别安全告警
   - 暴露面异常、认证缺失、配置显著失守

3. **用户很快会撞到的可操作问题**
   - update available 且影响兼容性
   - docs/FAQ/next steps 已明确给出排查入口
   - 某些 warn 会在常见操作中反复触发

4. **纯信息性内容**
   - 版本、统计、一般性建议
   - 没有当前动作价值的背景项

## 何时值得单独沉淀

适合单独写成短卡的，不是“status 里有什么字段”，而是：

- **如何给输出分级**，避免一股脑全追
- **什么算立即处理，什么算以后再说**
- **何时应顺着 next steps / FAQ 下钻，而不是自己发明排查顺序**

## 不该做什么

- 不要把 status 每个板块都重述一遍
- 不要把 update / warn / next steps 分别拆成过细碎片，导致文档簇再次过密
- 不要因为刚跑过 status，就把“继续围绕 status 本身写卡”误当成默认后续路线

## 实操口令

> 先把 status 当分诊台：先挑阻塞项和高价值 follow-up，其他信息性输出默认停在“知道有这回事”就够了。
