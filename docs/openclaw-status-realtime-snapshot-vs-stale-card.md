# OpenClaw Status Realtime Snapshot vs Stale Card

## 结论

当 heartbeat 需要基于运行态做低打扰沉淀时，优先区分“这是刚跑出来的实时快照”还是“只是上一次心跳留下的旧描述”。只要能拿到新的 `openclaw status` 输出，就应把它当成新证据；不要因为之前某次失败过，就继续沿着“失败信号”写边界卡。

## 判断口

1. **先看证据时间性**
   - 本轮成功跑出 `openclaw status`：这是实时快照。
   - 只有旧日志、旧记忆、旧口头描述：这是历史背景，不是当前状态。

2. **再看主题是否该切换**
   - 如果旧主题是“status 命令失败怎么办”，而本轮命令已恢复成功，就该停止围绕失败路径继续拆卡。
   - 新短卡应服务于“如何使用刚拿到的实时快照”，而不是继续消费已经失效的异常假设。

3. **最后看产出是否低打扰**
   - 只压缩一个新判断口：如何避免把旧快照/旧失败当成当前事实。
   - 不顺势扩成完整 healthcheck 或 security audit 工程。

## 默认动作

- `openclaw status` **成功**：围绕“实时快照优先于旧状态叙事”沉淀一条规则。
- `openclaw status` **失败**：才进入失败分支，按最小判别范围继续。
- **没有新命令结果**：不要假装拿到了当前状态，也不要复述上次快照。

## 为什么

heartbeat 的低打扰学习很容易掉进“拿着旧异常一直写 follow-up 卡”的惯性。真正该保留的经验不是某次失败本身，而是**一旦实时快照回来，就立刻让新证据接管叙事**。

## 实操口令

> 新 `openclaw status` 一旦成功，旧失败自动降级为历史背景；后续判断以当前快照为准。
