# OpenClaw Status Timeout Signal Handling Card

## 结论

当 `openclaw status` 一类总览入口在 heartbeat 中不是报错退出，而是被外部 `SIGKILL`/超时杀掉时，默认应把它归类为**本轮运行态取样失败**，而不是直接升级成“系统已坏”或继续连环重试。

## 为什么要单列

“立即失败”和“跑着跑着被杀掉”不是一回事：

- **立即失败** 更像命令入口、参数、环境初始化或可执行层面的问题。
- **被杀掉/超时** 更像等待链路过长、下游无响应、资源受限，或执行窗口不适合在 heartbeat 里继续消耗。

如果把两者混成一个信号，后续就容易：

- 误把一次取样失败讲成稳定故障
- 在 heartbeat 里反复重跑同一入口
- 用旧快照替代当前状态，造成口径漂移

## Heartbeat 下的默认动作

1. **记录这次属于“取样被杀/超时”而非“明确失败退出”**。
2. **停止在本轮继续追打同一命令**，避免把低打扰学习扩成排障工程。
3. **只沉淀一个边界**：说明未来若再遇到同类信号，先判断是“入口错误”还是“执行窗口/响应链路异常”。
4. **没有新确定性信息时，回复 `HEARTBEAT_OK`**。

## 不该做的事

- 不该因为看到 `SIGKILL` 就直接宣称 gateway 挂了
- 不该在同一轮 heartbeat 连续试三四次 `openclaw status`
- 不该拿上一次成功的 status 快照冒充当前实时状态
- 不该把“命令被杀”自动扩张成完整 root-cause 分析

## 后续若要继续

只有在后续明确需要排障、且不再受 heartbeat “低打扰”约束时，才值得继续拆：

- 是命令本体卡住
- 是下游服务响应慢
- 是执行环境资源/时间窗导致被杀

在此之前，先把它当作**一次未完成的采样**，而不是一个已经判明的系统结论。
