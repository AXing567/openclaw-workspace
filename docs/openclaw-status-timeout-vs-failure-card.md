# OpenClaw Status Timeout vs Failure Card

## 结论

在 heartbeat 场景里，`openclaw status` 不只会出现“立即失败”；还可能表现为**长时间无输出后超时/被杀**。这种结果应优先归类为“状态入口卡住或响应过慢”，而不是和“立即失败”混成同一类，也不能据此直接断言 OpenClaw 整体不可用。

## 为什么要单独区分

`立即失败` 与 `无输出卡住` 代表的判别方向不同：

- **立即失败** 更像命令入口不可执行、参数/版本/环境立刻报错。
- **无输出超时** 更像入口已启动，但内部检查链路、子探测、环境响应或 CLI 自身等待阶段卡住。

如果把两者混写成同一类“status 失败”，后续 follow-up 很容易选错方向。

## heartbeat 下的默认处理

1. **先记录现象本身**：命令启动了，但在可接受窗口内没有产出有效输出，最终超时/被杀。
2. **不要复用旧快照**：这轮依旧没有拿到实时状态，不能拿之前成功的 status 顶替。
3. **不要直接升级成系统故障**：卡住只说明状态入口响应异常，不足以直接证明 gateway 挂了或 OpenClaw 全面不可用。
4. **单轮到此为止**：若当前只是空闲学习沉淀，记录边界后收手，不在 heartbeat 里继续扩成多层排查。

## 推荐表述

- “这轮 `openclaw status` 不是立即报错，而是无输出卡住后超时；应先视为状态入口响应异常，而不是直接当作系统已故障。”
- “由于没有拿到新快照，当前不能复用旧 status 结果冒充实时状态。”

## 后续判别方向

如果以后用户明确要排障，再继续问更具体的问题：

- CLI 是否每次都卡在同一阶段？
- 是偶发卡顿，还是稳定复现？
- 其他更小粒度命令是否也卡住？

但这些不属于 heartbeat 默认动作。

## 实操口令

> `openclaw status` 若启动后长时间无输出并最终超时，先把它记成“入口卡住/响应异常”，不要和“立即失败”混写，也不要在 heartbeat 里顺势展开整套诊断。
