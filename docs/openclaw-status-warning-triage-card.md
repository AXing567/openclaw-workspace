# OpenClaw Status Warning Triage Card

## 结论

跑完 `openclaw status` 之后，若输出里同时出现 **可升级提示**、**security audit warn**、以及 **gateway 正常**，默认不要把“有 warning”直接讲成“系统异常”；先按影响面把 warning 分层，再决定后续该追哪一条。

## 默认分层

按下面顺序看：

1. **服务可用性**
   - gateway 是否正常
   - 核心进程是否在线
   - 当前会不会直接影响消息、节点或自动化能力
   - 这层异常优先级最高

2. **安全风险级别**
   - security audit 是 `critical`、`high`、还是普通 `warn`
   - 是否已经涉及公网暴露、弱口令、未授权入口、明知危险配置
   - `warn` 需要看，但不该和服务已坏混为一谈

3. **维护性/可升级性**
   - update available
   - next steps 给出的官方下钻入口
   - 这类通常影响“该不该安排维护窗口”，而不是“现在能不能用”

## 判断口

看到 status 输出里“有 warn”时，先问三句：

- **它会不会阻断当前功能？**
- **它是不是高危暴露，而不只是一般提醒？**
- **它更像立即修，还是应该排进维护队列？**

如果前两句答案都是否，那么默认把它归到“应关注，但非当前故障”。

## 为什么

`openclaw status` 容易把不同层级的信息并排展示。若不先分层，就会把“服务在线但有维护提醒”误读成“系统整体不健康”，导致后续建议失真。

## 回答模板

可用下面这种压缩口径：

> 先区分三层：服务是否可用、安全是否高危、维护是否该排期。gateway 正常说明主服务在线；security audit 的 warn 代表有待处理项，但不自动等于故障；update available 更偏维护窗口问题。

## 反例

以下说法都不够准：

- “status 有 warning，所以系统现在不稳定。”
- “看到 update available，优先先升级再说。”
- “有 audit warn，就默认所有后续问题都先怪安全配置。”
